## Purpose and conceptual model
A hosted review is a provider-qualified repository/number identity with a current head. The active workspace can link or suppress a review independently of the provider's review state. Checks follows that workspace; a PR detail page can inspect another review without changing the workspace. Creation operates on the exact current branch and confirmed eligibility. All surfaces use the canonical hosting API, never renderer subprocesses or a second merge/auth policy.

Daemon-owned state contains navigation, active tab, comment audience/grouping, expanded checks, selected file/view mode, queued comments, drafts and agent-dialog context. UI commands and mutations have generated namespaced API/CLI routes. Useful retained data survives transient failures; initial loading, no-review, unavailable and no-checks are distinct.

## Scope and non-goals
The union of all three assigned parts is required: hosting-ui.md section5 PR page, section10 Checks sidebar including every empty state, section11 creation and Source Control chain, and non-task settings in12. PR sitter, Tasks/issue/Projects implementations, provider APIs and new-workspace internals remain their owners. Reuse their public methods/contributions. GitLab and other-provider API items are currently blocked; their unavailable integration must be explicit, never a fake successful MR/create implementation. Any genuinely unavailable provider flow requires a recorded deferred decision and queued dependent follow-up under LOOP.md, not silent deletion.

## Decisions locked
- **Layout/density:** compact Checks sidebar and full-page PR with header, three tabs and a right actions rail. Keep target identity and errors visible; resize/scroll within pane rather than overflowing actions.
- **Loading/errors:** retain stale data with an alert and Retry; uncached failure differs from definitive empty. Disabled controls explain the actual blocker. Unknown merge metadata/checks is not success.
- **Interaction:** accessible labels and keyboard controls; Escape belongs first to an open dialog/editor; Cmd+Enter submits once. Dialog cancellation preserves content where documented. Commands act on the same daemon state the window reads.
- **Links:** HTTP(S) identity only; use shared link routing and native clipboard delivery. Shift+Cmd on macOS flips configured in-app/system target. Browser proof never claims native clipboard/focus success.
- **Authentication:** display canonical CLI/provider/account diagnostics, no OAuth/token editor or credential persistence. Repository binding fails closed; Projects ambient behavior stays unchanged.
- **Writes:** optimistic reversible edits with error rollback and context/generation ownership; merge becomes merged only after confirmed success. Kernel confirmation and expectedHead apply to human and plugin calls. No retry of mutations.
- **Persistence:** durable creation defaults and bot overrides, repository overrides/account selection scoped correctly. UI navigation/drafts remain session-owned. Head/target changes invalidate stale references and pending detail ownership.
- **Platforms:** macOS build/test only; other-platform native behavior remains explicitly unverified.

## Essential coverage and rationale
Consumer: local developers/agents replacing Orca. Outcome: inspect checks/comments/diffs, act on reviews, create/link PR and configure hosting entirely within Quirky. Boundary: canonical hosting policy and registered repo/worktree identity; public UI host, not private Orca renderer state. Success: all acceptance flows against real daemon/CLI plus visible web goals; native-only pending handoffs clearly distinguished. Errors: preserve data/draft and show action-specific reason, never silent success. Constraints: plugin-only, isolated state, one item, no asks, macOS-only verification.

Alternatives: shell-owned review components couple core to hosting; expanding Tasks concurrently risks shared writes and prevents replacement. A separate review plugin with public Tasks navigation and canonical hosting calls keeps three vertical implementation components independent without a second provider policy.

## Glossary
- **Review target:** source-qualified worktree/provider/number, independently of currently visible workspace.
- **Eligibility:** current canonical provider/git verdict, never inferred from stale UI metadata.
- **Queued:** provider accepted queue/auto-merge, not confirmed merged.
- **Suppression:** local workspace hides a specific review without closing it upstream.
- **Generation:** request ownership boundary across target/head changes and mutations.

## Technical decisions and contracts
The public integration mapping supplies exact hosting/UI/git/worktree/AI method names; reuse those rather than adding parallel provider policy. Commit shared interfaces in plugins/quirky.reviews/src/contracts.ts before implementers. Parent owns main.ts, ui.tsx, manifest/package/build integration, shared environment and test harness. ComponentA owns src/detail/ and test/detail.test.ts; ComponentB owns src/checks/ and test/checks.test.ts; ComponentC owns src/create/ and test/create.test.ts. Their method factories accept ReviewsEnv and return Record<string,MethodHandler>; UI components accept ReviewsSurfaceProps. Parent alone composes registrations. All state changes go through synchronous atomic env.update, increment revision and emit changed; readonly observations use public context.call. Durable settings/suppression persist; navigation/drafts are session-local. Component scopes do not overlap; no worker commits/build/lint/formatters/full suites. Parent runs affected suite/scripts/typecheck, one final cross-family review/fix batch, visible dogfood and normal queue landing after pending dependencies ready.
