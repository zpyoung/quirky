# Create a worktree from a GitHub PR or issue

## Status & amendments
Approved autonomously under docs/loop/LOOP.md night mode, 2026-10-27. One combined logic/technical spec; self-reviewed against the source feature flows. No open human questions.

## Purpose and conceptual model
A selected GitHub work item is a source, not a workspace name. The composer, CLI and API use the existing worktree creator. Hosting resolves authenticated work-item identity; the creator owns Git, paths, hooks, metadata and activation. PRs start at their exact head and keep their head branch name. Issues create an ordinary branch from the chosen/default base. Both retain durable linked-work identity independent of editable notes.

## Scope and non-goals
In scope: worktrees.md section 2 Smart #N/GitHub URLs, mixed GitHub search and selection/clear, PR-title naming/result metadata, same-repo and fork PR head creation, URL-scoped tracking refs, correct push targets, linked PR/issue records and the configured issue command in an independent terminal. Existing setup/agent/create-more/activation behavior remains.
Non-goals: GitLab MRs/issues, Jira, Linear, other worktree flows (cleanup, sorting/filtering, external detection), hosting review UI, native-only behavior, new account/auth infrastructure. Plain-name and existing-branch creation remain supported; no new lifecycle or private cross-plugin imports.

## Decisions locked
- **Input/selection:** Smart plain text offers a name choice; #N and HTTPS GitHub work-item URLs are authoritative lookups. GitHub tab searches issues and PRs, labels their kinds, displays loading/empty/errors and lets the person select, open externally and clear. Project/tab/query changes invalidate obsolete results. A failed explicit lookup cannot create a name-only workspace. Name/branch modes remain usable without hosting enabled.
- **Identity/auth:** use hosting's existing trusted configured repository and account rules. #N follows its configured issue/PR candidate order; a URL names a configured repository exactly. Not-found, unavailable and auth/rate-limit errors remain distinct. Never acquire GitHub credentials in worktree/UI code.
- **Naming:** source title is the default display name and sanitized folder name; explicit name/display/comment overrides retain existing semantics. Default note is `PR #N — TITLE` or `Issue #N — TITLE`. PR branch is its exact head ref name, not the title; no prefix or silent alternate checkout. Existing matching branch may be reused only at the selected head and not checked out elsewhere. Diverged/occupied branches fail without reset. A PR source conflicts with caller branch/branchName/base overrides; an issue may use base/branchName but not existing branch.
- **Checkout/tracking:** fetch the PR head from the matching configured base repository remote into a URL-hashed `refs/quirky/pull/<remote-component>/<number>` ref with a 60-second noninteractive network bound. Never reuse a stale ref on fetch failure. Verify fetched commit equals the fresh authenticated head OID; fail if moved. Persist compare base as the PR's base branch, not the synthetic pull ref. Reused PR branches are preserved on deletion.
- **Push:** if head repository matches a configured remote, use that remote and head branch. Otherwise provision deterministic `pr-<owner>-<repo>` fork remote, matching origin's SSH/HTTPS scheme. Never overwrite an existing remote pointing elsewhere. Track the real head branch and set branch pushRemote; never push into refs/pull or the base repository by accident. Preserve maintainerCanModify in metadata; false does not imply the actual fork owner cannot push.
- **Issue command:** support local Project Settings `issueCommand` and top-level quirky.yaml/orca.yaml issueCommand, merged under existing commandSource policy. Interpolate `{{issue}}` with decimal number and `{{artifact_url}}` with the canonical validated URL; title/body never become executable text. Run only for issue sources, alongside setup in a separate `Issue #N` terminal/split, without stealing focus; use bounded daemon execution if sessions disabled. Shared content is hash-trusted like setup; refuse before creating a worktree unless trusted or explicit trustIssueCommand. `issueCommand: skip` suppresses it. Local configuration is trusted. Post-create execution failures are warnings, not rollback.
- **Existing invariants:** setup decision/trust uses the selected checkout commit before branch/path creation; serialized per-repo create, collision suffixes, contained paths, generated-name retirement and guarded window activation remain. CLI/API never activate unless asked. No silent fallback from PR fetch to local/default branches.

## Glossary
PR head: contributor branch and exact commit. Base: branch receiving the PR and workspace compare base. Synthetic pull ref: URL-scoped read-only local ref fetched from refs/pull/N/head, never a push destination. Linked work: provider/repository/kind/number/title/URL metadata. Issue command: trusted project command template started for a selected issue.

## Technical decisions and shared contracts
- Add shared `GitHubRepositoryIdentity`, `GitHubWorktreeLink`, `GitHubWorktreeSource` and `WorktreePushTarget` types in packages/protocol/src/model.ts. Worktree optional nullable linkedPR/linkedIssue/pushTarget fields are additive; creator/list emit them where known. ProjectSettings.issueCommand and EffectiveHooks.issueCommand are additive. WorktreeCreateResult.issueCommand mirrors setup outcome.
- `quirky.hosting/worktreeSource({worktree?: string, reference: string}): Promise<GitHubWorktreeSource>` is a fresh authenticated read. reference is #N or a validated HTTPS GitHub work-item URL; not found throws typed not_found. Issue result has head/base null. PR result requires validated head/base repository identity, branch and full OID, canonical SSH/HTTPS clone URLs and maintainerCanModify. Use existing scoped runner/resolveWorkItem authorization, not a raw arbitrary API. Do not trust caller-supplied checkout tuples. Validate clone host/owner/repo against established identities; deleted/malformed heads fail closed.
- `quirky.worktree/create` gains github?: string, issueCommand?: 'run'|'skip', trustIssueCommand?: boolean. `quirky wt create --repo PROJECT --github '#3'` uses same handler. Existing API payloads remain valid. Daemon calls worktreeSource with registered primary workspace selector and source reference. New protocol fields are not consumer-supplied authentication.
- Hosting implementer owns hosting plugin source/manifest/tests only. Runtime implementer owns worktree daemon/main/CLI/manifest/tests plus repo hook/settings/CLI/manifest/tests. UI implementer owns worktree React/actions/report/sidebar/tests and repo settings React files only. Shared model changes are committed before workers start. Parent owns docs, integration and final checks. No private plugin imports, no protected loop file changes, no worker commits or broad test runs.
- Migrations append only. Store linked metadata as validated JSON fields or columns in worktree store, project issueCommand in existing project settings JSON. Preserve reconciliation against Git registrations/birthtime.
- API/CLI integration fixtures use fresh temporary QUIRKY_HOME; external gh is an isolated executable fixture and Git repositories/remotes are local bare fixture repos. A fixture git URL rewrite may map canonical forge URLs to local remotes without network, but production validation is unchanged. Stop owned processes and remove fixtures.
- Acceptance commands after integration: `bun scripts/suite.ts plugins/quirky.worktree plugins/quirky.repo plugins/quirky.hosting packages/protocol packages/git`; `bun test scripts`; `bun run typecheck`; `bun run build`. No pre-land whole suite; land owns it. Workers do not run checks mid-flight; parent runs owned behavioral tests at the barrier, recording failing-before proof against baseline when feasible. Guarded dogfood runs Smart PR/URL, GitHub mixed selection/clear and issue creation, error/reset and metadata/card outcomes against packaged web UI.
