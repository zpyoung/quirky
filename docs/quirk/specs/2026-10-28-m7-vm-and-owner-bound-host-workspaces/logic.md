## Goal, consumers and conceptual model
The local owner registers an authenticated remote daemon, projects its actual workspaces without copying paths locally, navigates that projection and performs destructive operations only against its exact host generation and workspace instance. Trusted repository environmentRecipes provision genuine Lima virtual machines and attach actual guest workspaces through the same owner transport. Phone and federation credentials remain narrower, unchanged authorities.

Host identity is generated by the remote daemon, persisted across restarts and paired with a fresh activation generation. A saved target is a credential locator, not host identity. A registration pins both the authenticated saved grant and remote identity. Mirrors are projections, not ordinary local worktree rows; they can never enter local filesystem cleanup/removal. Unknown/disconnected/replaced owners block operations. An old snapshot is not permission to delete.

## Decisions locked / gray areas
- API/authentication: reuse encrypted owner-cli runtimeCall, with an optional expected host identity/generation checked on the same authenticated connection before forwarding. Never widen phones, federation or infer host identity from labels, UI UUIDs or remote paths.
- Identity/data mapping: remote stable ID plus activation generation and canonical workspace instance ID. Registrations and mirrors persist. Refresh marks offline explicitly and never substitutes local results. Replacement requires explicit re-registration; stale generation rejects before side effects.
- CLI/output/errors: existing generated plugin namespaces, declared schemas and structured errors; destructive operations require explicit confirmation. No uncertain destructive retries.
- Sync/conflict: owner-to-local read projections only. Fresh owner evidence is required for refresh, navigation, cleanup preview and removal. Instance changes invalidate old mirror selections/fingerprints.
- VM lifecycle: macOS Lima backend, explicit executable availability, recipe hash trust and required lifecycle commands. Provisioning is a bounded subprocess, never a terminal tab. Verify the actual Lima VM and authenticate the guest daemon before attachment. No fake local VM fallback. Persist operation/error state so failed or interrupted lifecycle operations remain visible and recoverable.
- Attachment: provisioned-root attaches an existing guest workspace; orca-worktree creates a canonical guest worktree. Workspace ownership is authenticated through the registered guest host. Suspend/resume/destroy update attachment availability only after real backend outcomes; destroy-disabled recipes refuse destructive lifecycle.
- Platforms: build on macOS only. Linux/Windows host support is not claimed.

## Candidate approaches and rationale
Chosen: extend CLI owner forwarding with host fencing; extend the worktree plugin with separate registered-host/mirror and Lima-lifecycle owners. Rejected: duplicate transport/credentials; falsely turn recipe strings into local default tabs; use a native Swift app as the shell; make remote paths local worktree rows. A direct Apple Virtualization helper would add another runtime and packaging authority; Lima supplies a real supported VM runtime without changing the locked shell architecture.

## Behavior and acceptance scenarios
1. **Authenticated host registration and restart fence.** Before: two private owner runtimes and a saved owner grant. Register the target, list and restart local registration owner; stable host ID and saved grant remain. Restart remote owner: its host ID remains but generation changes. Old registration refuses forwarding until explicitly re-registered. A phone target, arbitrary label and changed grant cannot register or mutate.
2. **Remote mirrors and navigation.** Before: actual remote Git workspace with instance A and unrelated same-path local workspace. Refresh remote mirrors and navigate selected exact window. After: a remote-specific view reads actual owner data, never activates the remote path locally; other windows/local workspaces remain unchanged. Offline owner yields explicit unavailable state, not empty success. Replaced instance A→B cannot reuse old selection.
3. **Owner-bound removal and cleanup.** Before: mirror snapshot and cleanup fingerprint. Preview against live owner; mutate workspace or host generation, disconnect, revoke grant or reuse path, then remove with old evidence. After: each stale/unknown case refuses without local or remote deletion. Confirmed current selection invokes canonical remote safe cleanup/removal and only then retires its mirror; local same-path data remains untouched.
4. **Recipe validation and trust.** Before: repository config contains valid recipe and invalid entries. Invalid ID, missing backend, untrusted or changed exact lifecycle hash, unsupported checkout mode and destroy-disabled action fail before any VM/workspace resource mutation. Backend failures may retain a diagnostic failed-operation record; an invalid trust hash cannot start provisioning. Trust covers the complete recipe, not only create. Diagnostics identify the missing prerequisite without claiming VM completion.
5. **Real VM create and attachment.** Before: Lima installed, recipe scripts and guest owner endpoint available. Trusted create provisions the named real VM; verify backend and guest identity. Provisioned-root attaches an actual guest workspace; orca-worktree creates one through canonical owner worktree create. After: durable VM record binds exact backend instance, guest registration and workspace mirror; no local path copy. Failed script, malformed attachment, mismatched guest or lost response preserves visible failure/recovery evidence rather than inventing success.
6. **Suspend/resume/destroy.** Before: attached VM. Invoke supported lifecycle scripts and verify actual backend state. Suspension makes attachments unavailable; resume revalidates current guest generation before reattachment; confirmed destroy executes actual VM destruction and retires attachments only after success. Unsupported/missing lifecycle and disabled destroy refuse. Concurrent/stale lifecycle requests serialize and cannot target a replacement VM. Restart during an operation does not report completion.
7. **Native prerequisites retained.** Supported public SDK notification permission/click/dismiss callbacks and authorized production terminal-host signing/launchd/TCC/admission/upgrade identity remain external obligations, not fabricated delivery. Existing native handoffs and canonical Browser/automation owners remain unchanged.

## Defect prevention
Host/path duplicates cannot cross-talk; caller labels never grant ownership. Generation/instance changes invalidate destructive evidence. Unknown/disconnected remote liveness is not inactivity. No local fallback after remote failure; no destructive replay after ambiguous failure. Trust changes require fresh exact-hash consent. A normal shell command cannot be called a VM lifecycle.

## Scope and non-goals

Native callbacks/signing require outside capabilities and are recorded separately, not silently dropped.
