# Mobile daemon and desktop pairing

## Status & amendments
Approved autonomously under build/roadmap LOOP.md night mode, 2026-10-27. Technical contracts are included below; no separate tech.md or spec-review round.

**Amendments:** None.

## Purpose and conceptual model
A phone is an authenticated, encrypted, limited client of the same Quirky daemon API as the desktop and CLI. The desktop creates a durable per-device bearer credential and shows a QR containing that credential, the desktop's pinned X25519 public key and a reachable direct endpoint. Only successful sealed authentication promotes the pending offer into a paired phone. Revocation durably removes its credential and disconnects all its sockets and terminal streams immediately.

The mobile listener is owned by the replaceable built-in `quirky.mobile` plugin. It is separate from the existing desktop HTTP/UI listener, so widening mobile access never exposes static UI, plugin assets, health or hook routes. The kernel contributes only a public authenticated-client admission API. All feature methods, CLI commands and UI belong to plugins.

## Scope and non-goals
In scope: mobile.md Transport; Pairing identity/offers/registry/revocation (direct mobile scope); Encryption v2; RPC authorization; desktop flows 1,2,10 and desktop phone-driving/phone-fit in flow 7. Includes sidebar visibility, onboarding badge, install-stage platform/channel selection, settings pane, machine name, ranked/refreshed/custom addresses, QR enlargement/copy/regenerate, paired detection, revocation, auto-restore and take-back controls.

Out: phone app implementation, phone onboarding/home/workspace/session/source-control/files/tasks/accounts/settings screens (flows 3–9 except desktop overlay), phone credential stores/reconnect/downgrade latch, push, voice, mobile page bundle, remote-runtime grants/device-key forks, desktop-to-desktop delegation, cloud relay. The later phone fork targets Quirky's JSON-RPC and `quirky://pair` URL; no legacy Orca RPC aliases or v1 handshake. Hosted relay is prohibited by architecture.md. Windows firewall UX and Linux/Windows execution are deferred platform work. Incompatible Orca store links must not be represented as Quirky downloads; install availability must be truthful until the phone fork is shipped.

## Data flow
Generating a pairing offer resolves the chosen address and actual bound port, widens only the mobile listener, durably creates or reuses a pending token, then encodes a v2 offer and QR. A phone opens `/rpc` on that listener, sends hello, verifies the ready public key against the QR, derives transcript-bound directional keys, then authenticates inside the sealed channel. The plugin validates the token against durable state and admits a mobile client through `context.clients.accept`. Decrypted JSON-RPC requests use the ordinary dispatcher; text replies/events and binary terminal streams are sealed by the transport. Every request revalidates the credential and exact allowlist before dispatch. Admission and cleanup cannot be bypassed by `client.hello`, request-supplied role/device fields, idempotency or confirmations.

Terminal attachment by an authenticated phone claims an input/viewport lease automatically. Desktop output continues while desktop typing is paused. Take back releases that lease and restores saved desktop dimensions; the still-connected phone can watch without resizing or typing until it explicitly claims again. Leaving the last phone keeps phone-fit indefinitely by default or restores after the configured delay. No client-provided device ID is trusted.

## Decisions locked
- **Authentication/versioning:** v2 only, strict hello/ready/auth shapes, direct transport context, canonical base64, persistent pinned identity, bearer token only inside E2EE. Quirky JSON-RPC 2.0 requests and existing binary stream protocol, not Orca envelopes.
- **API authorization:** closed exact method list, no prefix wildcard, no plugin/admin/pairing/settings unrestricted access. Allow only explicit consumer methods and parameter-restricted safe settings/terminal operations. Local clients and trusted plugin calls remain unchanged. Authorization precedes cached request results and nested confirmation execution.
- **Error responses/limits:** bounded payloads, sockets, pre-auth lifetime, reply buffers; failures have stable machine-readable codes. Never advertise an endpoint when widening or durable credential creation failed.
- **Layout/information density:** use existing theme and plugin slots, intro → install → pair → paired, Settings > Mobile links to a dedicated contributed settings view. Inline pending/error/empty states and copy fallback. No fake success when clipboard or QR encoding fails.
- **Data durability/idempotency:** one pending token, reuse unless rotate, durable successful-auth transition, secure atomic writes, fail closed on unreadable identity/registry; no silent identity replacement. Custom address list max 50, bounded strings, no wildcard or zero-port endpoints.
- **Integration/conflicts:** the mobile listener never widens the desktop UI listener; each socket gets authenticated identity and connection lifecycle from the public API. Terminal server is the only lease/size authority; FitAddon reports desktop dimensions without stealing the phone lease.

## Key decisions & rationale
Recommended: feature-owned mobile transport plus a generic public admission API. It preserves loopback UI security and plugin replacement while sharing the actual dispatcher and terminal streams. Rejected: widen the desktop listener (exposes UI/assets and shares desktop token path); implement an independent RPC proxy (duplicates authorization/stream/cleanup semantics). Reuse source crypto helpers where possible, with attribution, rather than creating a new cryptographic construction.

Before: interfaces include Tailscale, Wi-Fi, IPv6, virtual bridge, loopback/link-local and 198.18/15 fake IP. ### A3: Pending offer and QR
Before: empty registry. Generate twice without rotate: same device/token; pending is not in devices list. Rotate: previous pending token becomes invalid; paired devices remain valid. After durable row creation return `quirky://pair?code=<unpadded-base64url-json>` with v2, endpoint, 48-hex token, canonical 32-byte publicKeyB64, pairedDeviceId, mobile scope. QR uses error correction M, 4-module margin, scale 2. Encoding failure returns null QR plus encoding_failed, retaining copyable valid URL. Write failure returns device_registry_unavailable and no issued credential. Token never appears in list/state/events/logs.

### A4: Key and registry durability
Before: initial identity/registry absent. Create once with mode 0600 under private plugin data dir using atomic durable security writes. Restart: same public key and valid paired token. Unreadable identity fails closed rather than unpairing devices. Malformed key file may be regenerated only when safely quarantined and cannot silently preserve credentials against a changed identity; prefer fail closed. Unreadable registry rejects writes/auth with registry_unavailable; corrupt registry quarantined before any replacement, never overwritten silently. Authentication's first lastSeenAt transition is durable before success. Revocation persists before disconnect/success, and remains revoked on restart.

### A5: Encrypted channel and authorization
Before: offer with pinned key/token. Fresh phone key/nonce sends strict v2 hello and direct context. Ready echoes nonce, provides fresh desktop nonce and pinned public key. Both independently derive same transcript hash, directional keys and session ID. First sealed text auth proves transcript and token; server replies sealed authenticated hash. Real encrypted status and terminal stream work. Unknown fields, noncanonical base64, wrong context/key/nonce/hash/token, low-order invalid peer keys, plaintext post-ready, malformed MAC/header/nonces, replay/gap/cross-direction/kind/session frames cannot dispatch. Pre-auth decrypt failure closes 4001; 10s handshake deadline 4002; five consecutive post-auth decrypt failures 4003. Oversize inbound is rejected at 1MiB. 128 WS/256 TCP cap and ping/pong 15s sweep reap suspended peers around 60s. Outbound JSON 4MiB/binary 8MiB; reply-too-large is request-scoped where possible; overflow closes 1013; process bounded buffered32MiB/queued128MiB/16384frames/256sources. At most16 concurrent requests per mobile device; runtime_busy on excess. Bound memory is freed on every disconnect.

After auth, mobile calls only literal allowlisted Quirky consumer method names. Disallow admin/installation/daemon shutdown/pairing generation/revoke/generic arbitrary settings mutations. Revalidate identity before every request, including concurrent revocation, repeated hello and idempotent paths; no credential, role or device spoof via params. Revocation closes all sockets/streams immediately and reconnect receives sealed unauthorized +4001. Three failed direct auths in60s produce one desktop toast per daemon session with Open Mobile Settings.

## Glossary
Pending: durable token never successfully authenticated. Paired: first authenticated connection durably recorded. Driver: authenticated phone connection holding terminal input/viewport. Phone-fit hold: last phone's dimensions retained after disconnect. Offer: secret-bearing QR/URL, not safe diagnostics.

## Technical decisions and shared contracts
### Architecture and ownership
- Generic kernel public API in `packages/protocol/src/plugins.ts`: `PluginContext.clients: PluginClients`. `accept` takes immutable mobile role/deviceId/name, live authorize callback, text/binary send callbacks and transport close callback; returns id, receive and disconnect. No raw daemon object imported by plugins. `PluginCaller.deviceId` is inherited from admitted connection, never client params. Core removes streams/subscriptions and revokes admitted clients on plugin disable/failure.
- Mobile shared public DTOs in `packages/protocol/src/mobile.ts` (exported by index): MobileDevice, MobileNetworkInterface, MobilePairingOffer, MobilePairingResult, MobileState, MobileTerminalState.
- Mobile transport/state/crypto plugin implementation and manifests: `plugins/quirky.mobile/main.ts`, `src/daemon/**`, `src/crypto/**`, `quirky-plugin.json`. Depends only on public protocol API, tweetnacl/qrcode and platform libraries; no daemon-private imports. Separate loopback-first mobile server 6768; environment `QUIRKY_MOBILE_PORT` permits explicit0 for isolated tests, `QUIRKY_MOBILE_HOST` pins bind host. Default host follows paired history, not desktop port. `/rpc` is sole upgrade path. Full resource ownership/stop in deactivate.
- Desktop UI: `plugins/quirky.mobile/src/ui.tsx`, `src/window/**`; existing build discovers src/ui.tsx. Contributed `sidebar-section:quirky.mobile/mobile`, `view:quirky.mobile/page`, `view:quirky.mobile/settings`, `command:quirky.mobile/open`, `command:quirky.mobile/open-settings`. Settings dialog adds a generic link to each plugin's declared open-settings command, reusing command dispatch, not mobile-private shell code.
- Terminal daemon/client integration lives inside `quirky.terminal`, using authenticated caller.deviceId/connection. MobileTerminalState is public; lease events `quirky.terminal/mobileChanged` contain only nonsecret state.

### Mobile API/CLI contract
All names prefixed `quirky.mobile/`, manifest schemas strict object params and generated CLI group alias `mobile`:
- `state {}` → MobileState (no secrets); `interfaces {}` → MobileNetworkInterface[].
- `pair {address?:string, rotate?:boolean}` → MobilePairingResult. Direct-only; chosen address or best OS address. Local API only, mobile allowlist denies it.
- `devices {}` → MobileDevice[]; `revoke {deviceId:string}` → `{revoked:boolean}`. Revocation is immediate without confirmation per feature source.
- `configure {machineName?:string, showMobileButton?:boolean, onboardingSeen?:boolean, autoRestoreFitMs?:number|null, customAddresses?:string[]}` → MobileState. Bounded nonempty machineName (max128), addresses max50/max16384 each, finite auto-restore clamp5000..3600000 or null; UI choices null/60000/300000/1800000. Caller mobile cannot use unrestricted configure.
- `open {settings?:boolean}` → existing `ui.view.open` result (view page/settings); CLI can reach full UI. `changed` event signals safe state invalidation, never offer/token.

### Terminal API contract
Existing `quirky.terminal/attach`, `write`, `send`, `resize`, `detach` retain their schemas (additional explicit `claim?:boolean` on attach/resize where needed). Mobile authenticated caller identity is authoritative and attach claims automatically. Add manifest methods `mobileState {session?:string}` → `{terminals:MobileTerminalState[]}`, `takeBack {session?:string}` and `restoreFit {session?:string}` → `{ok:true}`, local-only administration; optional session means all. Add `claim {session:string, cols:integer1..1000,rows:integer1..500}` for explicit authenticated mobile reclaim and local automation. CallerConnection is used for cleanup; leases survive neither revoked/disconnected phone nor terminal exit, while phone-fit hold can. Read autoRestoreFitMs via `quirky.mobile/state` or persisted public settings; avoid circular startup dependency. All desktop writes are rejected while an active lease exists, including CLI/session send routes that use terminal plugin. FitAddon records desktop viewport rather than stealing ownership. Existing unrelated terminal behavior remains unchanged.

### Encryption contract
Reuse upstream pure v2 helper semantics (source `/Users/zpyoung/PycharmProjects/orca/src/shared/mobile-e2ee-v2-*` and `paired-e2ee-v2-*`), preserving protocol domains `orca-mobile-e2ee` for the framing, not the RPC API. X25519+HSalsa20 from tweetnacl.box.before, strict hello/ready shapes exactly as mobile.md. Canonical base64 32-byte keys/nonces; SHA256 length-prefixed transcript domain `orca-mobile-e2ee/v2/transcript`; HKDF-SHA256 salt `SHA256(orca-mobile-e2ee/v2/salt\0||clientNonce||desktopNonce)`, info `orca-mobile-e2ee/v2/session\0||transcriptHash`,96bytes → direction keys/sessionId. Keep upstream deterministic24byte nonce and42byte authenticated plaintext header; frame overhead82bytes; uint64 counters advance only on valid authenticated frames. Sealed text is canonical base64 and binary raw. Auth exact `{type:'e2ee_auth',v:2,transcriptHashB64,deviceToken}` and success `{type:'e2ee_authenticated',v:2,transcriptHashB64}`. Reject invalid/zero shared secrets. Reject legacy plaintext credentials and all RPC until sealed auth succeeds.
