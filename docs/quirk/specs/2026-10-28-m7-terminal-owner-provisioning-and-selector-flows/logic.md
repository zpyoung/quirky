## Goal and conceptual model
A separately granted owner CLI can administer an exact saved or one-off runtime over the existing paired E2EE transport. The existing mobile device grant and federation peer grant never become owner credentials. Provider and ordinary worktree operations execute on the genuinely selected runtime, not locally under a remote label. Workspace views contain selectors, not necessarily canonical IDs; the worktree owner resolves them before navigation, history, sleep, close or cleanup decisions.

Consumers: local/remote CLI agents and desktop windows. Success: real owner pairing/admission/revocation and remote calls; canonical selector-to-owner lifecycle; source acceptance coverage of security, ambiguity and lifetime boundaries; exact final disposition for other inherited obligations.

## Decisions locked and alternatives
- API/CLI/authentication: reuse the existing listener, encryption and public kernel admission. Add a distinct durable owner-grant registry and `owner-cli` offer scope; strict mobile parsing still accepts only mobile offers. Grant creation requires explicit owner confirmation. Revalidate the current credential on every admitted request and close live connections on revoke. Never serialize secrets in grant/runtime summaries.
- Integration/data mapping: saved target identity pins endpoint, public key and grant. Public `quirky.cli/runtimeCall` requires an owner-scoped saved target and returns `{runtime,result}`. Provider/worktree integrations use `runtime:<selector>`; generic one-off CLI routing accepts an owner offer directly. Unknown/ambiguous/stale grants fail without local fallback. Existing phone-scoped routing remains narrow.
- Error/recovery/idempotency: retain namespaced schemas, generated CLI, request IDs and confirmation conventions. Revocation is idempotent, failed/empty model probes retain prior choices, and unknown ownership never becomes deletion authority. Do not automatically replay an uncertain destructive remote mutation.
- Visual/lifecycle: exact live kernel connId and complete-view close CAS remain authoritative. Resolve id:/name:/branch:/absolute path and supported view path inputs through existing worktree matching. Unknown/ambiguous workspace owners block lifecycle writes, even when another sleeping target was requested. Unrelated non-workspace views do not invent a workspace owner. Per-window history stores canonical IDs, not selector spellings; PTYs, drafts and buffers survive sleep.
- Provenance: durable desktop/client and worktree-host ownership require an authentic producer, not a phone ID, connection number or caller-supplied host label. New source must preserve unknown old records rather than backfill invented provenance.
- VM/native/platform: environmentRecipes are VM provisioning and attachment lifecycles, not shell tabs. Existing canonical blocked remote-automation owner, native Browser owner, supported notification callback prerequisite and production signing identity prerequisite retain their scopes. macOS only; Linux/Windows need separate work.

Chosen: extend three disjoint existing-owner components with contracts committed first. Rejected: duplicate transport/crypto/host/VM stores, widen mobile credentials, or count related completed features/refusals as missing-flow implementation. A third option, metadata-only remote ownership with local execution, is rejected because it cannot fence real side effects.

## Behavior and acceptance scenarios
1. **Owner grant lifecycle.** Before: private desktop runtime with an ordinary phone grant. Walkthrough: confirmed owner offer, connect a real E2EE client, read full API and perform owner-only config operation; try the phone token with the owner offer and spoofed identity; revoke the owner grant while connected and reconnect after restart. After: only genuine owner grant executes, registry summaries hide secrets, revoked credential and active connection cannot issue new calls, phone restrictions unchanged. Bad/corrupt registry never silently resets authority.
2. **Saved and one-off routing.** Before: two temporary runtimes and a local config marker. Walkthrough: save owner offer, call remote API via saved target then one-off offer, revoke or tamper with pinned target and retry. After: only selected remote changes, no local fallback, safe exact identity and error output. Existing mobile targets still work only within mobile authorization.
3. **Remote provider launch/hooks/config and discovery.** Before: authentic owner target and provider/account configuration. Walkthrough: route an actual public provider launch or hook/config operation to that runtime, then unsupported/failed/empty model probe and a real supported complete model-list protocol. After: remote operation uses remote accounts/process/home; no fake session or host labels; failed/unsupported discovery does not retire models. Exact remote-automation retirement remains solely its canonical owner after generation-fenced dispatch is available.
4. **Ordinary exact-host worktree create.** Before: genuine owner target, real remote repo identity and selected settings. Walkthrough: create through canonical remote worktree API and inspect returned remote identity; invalid target or denied grant first. After: actual remote checkout, no supervised-worker substitution or local checkout. Local prepared-pool/defaultTabs/tracker/icon behavior remains unchanged. A remote registration/view mirror cannot be invented from a local path.
5. **Durable desktop/host cleanup identity.** Before: two actual desktop clients, a phone origin, old unknown origin and a remote-owned row. Walkthrough: create/filter/restart, then disconnect/replace remote owner and scan/remove via fingerprint. After: actual stable creator/host alone classifies rows; unknown provenance stays unknown, owner replacement invalidates cleanup evidence, disconnected/unknown remote ownership blocks deletion. No connection-ID-as-durable-identity shortcut.
6. **VM lifecycle and attachments.** Before: configured VM recipe with create/suspend/resume/destroy and real execution/attachment authority. Walkthrough: trusted provision, attach, suspend, resume, destroy; invalid/untrusted recipe preflight first. After: actual owner-fenced VM and attached workspace lifecycle, not ordinary shell command tabs. No installed tart/lume/limactl/vfkit was found during orientation; this observation alone does not make reachable source engineering an external blocker.
7. **Canonical view selectors.** Before: two exact windows on known workspaces, active view input `worktree:"id:wt_id"` or `path:"/repo/wt/subdir"`. Walkthrough: back/forward/next/previous/index, sleep active subtree and stale CAS close; also unknown and duplicate-name selectors. After: canonical owner is used for history/selection and matching close; successful sleep closes the inspected target view only, unresolved/ambiguous owner refuses before sleeping changes; concurrently selected view is never closed. Bare IDs, folder paths and unrelated views remain valid. Cleanup also resolves view ownership conservatively.
8. **Native prerequisites.** Supported SDK notification permission/click/dismiss and authorized production helper signing/launchd/TCC/admission/upgrade cannot be fabricated. Retain existing pending native scenarios and prerequisite records; a void showNotification call is not lifecycle evidence.

## Technical decisions and shared contracts
- `packages/protocol/src/runtime-owner.ts` exports OwnerCliPairOffer (`v:2`, endpoint, deviceToken, publicKeyB64, pairedDeviceId, scope:`owner-cli`), OwnerRuntimeIdentity (id/name/endpoint/grantId), OwnerRuntimeCallParams (runtime/method/params?), OwnerRuntimeCallResult (runtime/result), WorkspaceViewOwner (worktreeId/instanceId). Public barrel export committed before dispatch.
- `quirky.cli/runtimeCall({runtime,method,params?}) -> OwnerRuntimeCallResult`: local owner resolves the saved target, requires owner-cli scope, opens existing E2EE client against pinned offer, calls exact method and closes resources. No mobile escalation, arbitrary credential envelope, identity leak or silent local fallback. `quirky.cli/runtimeShow` may expose safe scope/identity, never token. No cyclic calls to local owner forwarding; remote request targets the actual method.
- A scope: packages/protocol/**, packages/daemon/**, packages/cli/**, packages/ui/**, apps/desktop/**, plugins/quirky.cli/**, plugins/quirky.mobile/**. Own offer/grant/admission/revoke/routing and shared types if needed, tests/docs/manifests. Any durable desktop identity producer must be explicitly authenticated and committed with callers; do not invent one from connId.
- B scope: plugins/quirky.agents/**, plugins/quirky.accounts/**, plugins/quirky.agent-status/**, plugins/quirky.automations/** only for preserving canonical retirement boundaries. Own actual supported non-Codex probes and runtime-owner provider composition through the shared call contract, tests/docs/manifests. No A/C source edits or remote-automation substitute. Follow existing account preparation and bounded model-probe protocols.
- C scope: plugins/quirky.worktree/**, plugins/quirky.repo/**. Own canonical view selector resolution and all navigation/history/sleep/close/cleanup callers, ordinary owner-target remote creation where genuine contracts permit, provenance/cleanup only with authentic producer, tests/docs/manifests. ### Second-wave provenance consumer contract
The shared producer is committed in component c2825141, integrated at2c9fe15e. `PluginCaller.desktopClientId?:string` is set only by authenticated UI hello; `WindowRoute.desktopClientId?:string` comes from exact self connection. Workspace source stores it against the actual new worktree instance, never accepts a creator ID from create params, and exposes safe creator provenance for filters. A caller without producer cannot classify other clients. Reused paths/old rows/phone IDs must not inherit a desktop ID. Scope is plugins/quirky.worktree/** and plugins/quirky.repo/** only, including UI/API/CLI tests and docs. No schema/control primitive outside that component changes. This is a genuine semantic dependency on the producer, so it is a second wave, not overlap-only serialization.
