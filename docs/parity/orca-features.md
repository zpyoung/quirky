# Orca residual feature parity

This table records bounded Quirky equivalents and behavioral evidence for the residual features and goal-loop workflow. `covered` means a behavioral assertion exists, not that its latest CI result passed. It does not mean one small check verifies an entire plugin. `gap` names missing behavior, `excluded` records an explicit scope decision, and `delegated` assigns evidence ownership without claiming a pass. No row claims success from a method declaration, test filename, or planning inspection alone.

The three inventories have separate owners. Goal 10 owns browser commands in the [Orca browser parity table](./orca-browser.md); Goal 11 owns command groups and discovery in the [Orca CLI parity table](./orca-cli.md); this Goal 12 table owns residual daily-use features and the composite workflow. Both sibling tables are at those canonical paths. Goal 11 delegates 18 residual roots to Goal 12; this table reflects their feature, gap, exclusion, or delegation outcome without reproducing the command catalog. The workflow composes a subset of commands; it is not a third command catalog.

UI-facing Orca provenance is `documented-ui`, based on the locked feature selection in `BRIEF.md`, flows in `docs/roadmap.md`, and version-matched Orca guides for the new-agent tab, worktree cards, Settings, terminal layouts, and history. It is not `live-ui-observed`: no live Orca window was inspected or driven. BRIEF's referenced `research/orca-features/` inventory is not tracked in this checkout, so its contents are not inferred here.

Every check below is a literal single-file test command. An optional `title` is the exact test name; without one, the judge must inspect every test in that file. Explanatory text describes the assertion and is not part of the title. Multiple commands in one cell are separate checks, and the exporter preserves all of them. The table and checks are evidence to evaluate, not claims that the tests were run during authoring.

## Workflow translation notes

The Goal-12 rehearsal composes public Quirky operations instead of reproducing Orca spellings:

- Worktree creation uses `--base`, not `--base-branch`.
- `worktree create --agent` accepts catalog IDs rather than a fixed CLI list. Ordinary local creates validate explicit non-shell agents before allocating a worktree when the agent service is available. Without that service, launches without model/option picks retain the existing fallback; model/option picks require it.
- Quirky session IDs stand in for Orca terminal handles.
- `accounts usage` returns `providers[]`; `accounts list` is not Orca's `result.rateLimits` usage report.
- A Quirky removal receipt may retain an unmerged branch. If it does, cleanup must use the receipt's exact branch and head with `worktree delete-branch`, not raw `git branch -D`.
- Repeated loop turns use the native Codex fixture rather than a real Claude process. This does not attest a live Claude/model/account configuration. No harness file is migrated by this PR.
- Compound terminal commands use `/bin/sh -c <quoted script>` so the exec-based launcher runs the entire script, including its input read and final shell.

## Export shape and validation

`--json` emits a `FeatureTableExport`:

```ts
type FeatureTableExport = {
  schemaVersion: 1
  rows: {
    id: string
    disposition: 'covered' | 'gap' | 'excluded' | 'delegated'
    checks: { file: string; testTitle: string | null }[]
    reason: string | null
  }[]
  errors: { code: string; rowId: string | null; file: string | null }[]
}
```

The parser takes Markdown text, a repository root, and the not-on-CI list text. It accepts checks only as backticked `bun test <repo-relative-file>` commands, optionally followed by `title: \`<exact test name>\``. It validates required IDs, unique rows, reasons, check paths, and not-on-CI exclusions without executing a command. A not-yet-existing pending path is allowed only on a `gap` row. Any error produces an empty `rows` array; covered checks missing from the repository or listed in `scripts/test-not-on-ci.txt` produce `missing-check` or `check-not-on-ci`.

## Matching checks to main CI evidence

The exporter is an inventory validator, not a test runner or CI judge. It reads this Markdown table and `scripts/test-not-on-ci.txt`, validates them, and emits the `FeatureTableExport` shape. It does not read a baseline, make network requests, start subprocesses, or run any test named in the table. Check-list parsing uses the first whitespace-delimited path on each non-comment, nonblank line, as `scripts/suite.ts` does. The macOS-only list is not a not-on-CI exclusion; macOS tests run in the Tests workflow's macOS job.

Use this procedure when judging a main checkout:

1. Run `bun scripts/parity/feature-table.ts --json` from the checkout being judged and record its commit. Find the existing Tests push run for that exact repository, `main` branch, and commit. Do not substitute a PR run, nearest ancestor baseline, or unrelated successful workflow. If no completed run and artifact exist for that commit, record `unverified` and stop that ruling. If Actions is not running, report that; do not run tests locally or dispatch a workflow from this tool.
2. Read `baseline.json` from that run's `test-baseline-<40-character-main-SHA>` artifact. `verdict` in `scripts/test-baseline/cli.ts` publishes it from `out/baseline.json`; the artifact retains 14 days of results. Verify `version: 1`, `commit` equals the judged SHA, and `runId` equals the selected Tests run. A downloaded/cache copy at `<git-common-dir>/test-baseline/<SHA>.json` has the same content, but use it only when its provenance from that exact main run is established. The exporter does not download or write this cache.
3. For each `covered` check, look up `baseline.files[check.file]` and every `baseline.tests` entry whose NUL-separated key begins with that exact file. `files` contains `platform`, `durationMs`, `fileError`, and `flaky`; it is not a pass boolean. `tests` stores `passed`, `failed`, or `skipped` for `<file>\0<classname>\0<name>`. If `testTitle` is present, match the exact third component: zero or multiple matches are `unverified`, not a guessed result. Without a title, require at least one test and inspect every test in that file. A non-null `fileError` or any selected `failed` test fails the check. A missing file/test, unexpected platform (compare `scripts/test-on-macos.txt`), or any selected `skipped` test is `unverified`. Otherwise the check passes; retain the `flaky` annotation because a successful rerun is recorded as passed. A known main failure remains a failure even if it would not block a PR regression check.
4. A row passes only if all its covered checks pass. A `gap` remains unmet; an `excluded` row carries its written scope reason; a `delegated` row points to its named goal evidence without claiming a test pass. Any required failed or unverified check means parity is not established. Exporter exit 0 means only that the inventory is valid.

Raw per-file attempt evidence is also available: `run-shard` writes `FileResult[]` to `results/linux-<shard>.json` and `results/macos.json`, uploaded as `test-results-linux-<shard>` and `test-results-macos` with one-day retention. Prefer the normalized main baseline for the ruling; use raw attempts to explain failures and flakes. `out/verdict.json` and `out/comment.md` are comparison summaries, not per-file pass ledgers, and are not published as durable baseline artifacts. A green Tests job alone is insufficient because main's verdict is lenient about test failures while still publishing their results.

The exporter accepts only `--json` and `--help` and reads the fixed checkout-relative table/list paths. `--json` writes one JSON document to stdout. Valid inventory (including gaps) and help exit 0; read or validation errors exit 1 with JSON errors and no partial rows; unsupported or missing arguments exit 2 with usage on stderr. Export success is never a parity verdict.
