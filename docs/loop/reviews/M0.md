at `d2011e4`, 1989 tests pass and typecheck is clean. Three things need you before M1 starts:

- **One HIGH review finding is only partly closed** (see [Blockers](#blockers)).
- **The UI scenarios were never used like a user.** LOOP.md's step 6 rule for that, and the
  native-scenario handoff, landed in `d2011e4`, after every M0 item had merged. No M0 item ran
  `quirk:using-apps-like-a-user`, and `docs/loop/native/` doesn't exist. Decide whether to run it
  for M0 now or let M1's items cover the window.
- **The exit test runs on a throwaway repo.** The roadmap says a milestone's exit test passes "on
  real work, not a demo repo". [exit.e2e.test.ts](../../../packages/ui/test/exit.e2e.test.ts) creates
  a fresh git repo under `/tmp/qx-*`. Running the exit test's CLI steps against one of your repos

## What to look at first

These ten are the hard-to-reverse, medium-confidence decisions that every later milestone builds
on. Changing one after M1 means reworking plugins, the CLI surface or stored data. The full list,
sorted the same way, is [DECISIONS.md](../DECISIONS.md).

1. [m0-core D21](../decisions/m0-core.md): the daemon owns the window's layout, focus and visible
   view, and the selected worktree and session are the session view's input. There's no tab model
   beyond that.
2. [m0-core D11](../decisions/m0-core.md): the public plugin API grew by six members (`pty`,
   `notify`, `launchEnvironment`, `runLaunchHooks`, `home`, connection streams) so the built-ins
   need nothing private. This is now API that third-party plugins can rely on.
3. [m0-core D6](../decisions/m0-core.md): v1's methods were renamed to `<pluginId>/<name>` with no
   aliases, and the protocol went to version 2. Any v1 script that calls the API breaks.
4. [m0-core D5](../decisions/m0-core.md): the split into eight built-ins and their dependency
   graph. It decides what a distro can replace on its own.
5. [m0-scripting D10](../decisions/m0-scripting.md): plugin methods become `quirky <group>
   <method>`, with the group being the plugin ID minus `quirky.`, so third-party groups read
   `quirky acme.notes add`.
6. [m0-scripting D12](../decisions/m0-scripting.md): generated commands take only kebab-case flags
   and no positionals, with JSON for objects and `--params` for the whole object.
7. [m0-core D26](../decisions/m0-core.md): a distro is an overlay that removing it takes away, and
   only one distro can be installed at a time.
8. [m0-daemon-api D9](../decisions/m0-daemon-api.md): each plugin gets its own SQLite file and data
   directory, and nothing joins across plugins.
9. [m0-ui-api D6](../decisions/m0-ui-api.md): a slot hands the plugin one container element and
   nothing else of the page, with no shadow root.
10. [m0-registry D4](../decisions/m0-registry.md): contribution IDs are
    `<kind>:<pluginId>/<name>`. They're stored in disables, distros and settings.

## Memory

**`measure.py` didn't run against this build, because it only launches the Electrobun and
Electron probe apps.** Their paths are hard-coded, and it has no mode for Quirky. The typical-day
workload also can't run in full yet: it needs an editor (M2) and two terminal panes on screen, and
starting the desktop window is a foreground action the loop doesn't take.

What did run: the daemon side, measured the way
[quirky-v1-daemon.md](../../../research/memory-probe/quirky-v1-daemon.md) measured v1. One run on
a fresh temporary `QUIRKY_HOME` and a throwaway repo, at `d2011e4` on Bun 1.4.0, with sessions
created and driven through `quirky api call`. Numbers are macOS `footprint` phys_footprint in MB,
zsh excluded:

| Workload | quirkyd | quirky-pty | Total | v1 total |
| --- | --- | --- | --- | --- |
| Idle, one repo, no terminals | 20 | 12 | 32 | 25 |
| Four shells, empty | 20 | 18 | 38 | 30 |
| Four shells after `seq 1 10000` | 21 | 25 | 46 | 40 |
| Eight shells after `seq 1 10000` | 22 | 31 | 53 | 43 |

- `quirkyd` grew about 7 MB over v1 with all eight built-ins active, and sits far under its Bun
  budget of 60–100 MB.
- `quirky-pty` at eight busy sessions is 31 MB, a little over its budget of 10–20 MB plus under
  1 MB per session (at most 28). v1 measured 29 here, so M0 didn't cause this. The budget's own
  basis is a probe with four quiet shells. M1's terminal host daemon rewrites this process, and its
  item should re-measure.
- No UI client was attached and no structured session ran, the same caveats as the v1 numbers.

The script is `qmeasure.py` in this iteration's scratchpad. It's not in the repo.

## Test results

On `build/roadmap` at `d2011e4`:

- `bun run test`: 1989 pass, 0 fail, across 152 files (95 s).
- `bun run typecheck`: clean.
- `bun test scripts`: 13 pass, 1 fail. The failure is "docs/loop/queue.json > starts at the plugin
  kernel", which asserts the live queue's next item is `m0-registry`
  ([m0-daemon-api D31](../decisions/m0-daemon-api.md)). It has failed since m0-registry finished.
  The test is under the protected `scripts/build-loop/`, so you have to fix it, and until you do
  `queue.ts check` at the end of the roadmap will trip on it.

**Earlier test runs left orphaned processes behind.** Before this review there were twelve: eight
`quirkyd` and `quirky-pty` processes under `/var/folders/.../qx-*` homes from
`packages/ui/test/exit.e2e.test.ts`, run in iteration 6's deleted V1 worktree, and four
`packages/daemon/test/fixtures/fake-pty-host.ts` processes from runs between 06:48 and 16:03. Each
had parent PID 1. This review's own run left none, so the leak probably happens when a run is
killed or times out, and teardown never runs. LOOP.md says tests kill what they start. I stopped
all twelve. The daemon could tie the PTY host's lifetime to its own, or the harness could kill
the whole process group. That's worth an M1 item.
