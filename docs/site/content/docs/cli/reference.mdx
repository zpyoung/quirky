The `quirky` CLI talks to a running Quirky runtime. Use it when a shell script or agent needs to inspect worktrees, launch terminals, open files, automate the built-in browser, or report progress back into Quirky.

## Verify the runtime

Register the CLI under [Settings → General → Quirky CLI](/docs/settings), then check that it can reach Quirky.

<Callout title="On Linux the command is quirky-ide">
  GNOME Quirky — the screen reader that ships with most GNOME desktops — already owns
  `/usr/bin/quirky`, so Quirky's Linux CLI installs as `quirky-ide`. Do not check for it with
  `command -v quirky`: that succeeds on a GNOME desktop and resolves to the screen reader, not to
  Quirky. This page writes `quirky` throughout — read it as `quirky-ide` on Linux. See [Install →
  Linux](/docs/install#linux).
</Callout>

On macOS and Windows:

```bash
command -v quirky
quirky status --json
```

On Linux:

```bash
command -v quirky-ide
quirky-ide status --json
```

If Quirky is not already running:

```bash
quirky open --json
quirky status --json
```

Use `--json` when another tool will parse the result. Human-readable output is for quick terminal checks.

## Selectors

Most commands accept selectors instead of requiring long IDs:

```bash
quirky repo show --repo id:<repoId> --json
quirky worktree show --worktree active --json
quirky worktree show --worktree path:/abs/path/to/worktree --json
quirky worktree show --worktree branch:feature-name --json
quirky worktree show --worktree issue:123 --json
```

`active` and `current` resolve to the enclosing Quirky-managed worktree from the shell's current directory or terminal context. Use explicit selectors in scripts that may run outside the target worktree. For remote runtimes, prefer full server-side selectors such as `id:<repoId>::<absolute-worktree-path>` or `path:<absolute-server-path>` because the local shell's current directory may not exist on the runtime host.

## Choose a host

List every machine the current Quirky host can target and the selector for each one:

```bash
quirky host list --json
```

The result includes this machine, its registered [SSH targets](/docs/ssh), and paired [Remote Quirky Servers](/docs/remote-servers). Use `--host local` for this machine, `--host ssh:<target-id>` for an SSH target, and `--environment <server-name>` for a paired server. SSH rows include the detected remote platform (`linux`, `darwin`, or `win32`) after the target connects; older or disconnected targets report `platform unknown`. They also include `connected` and, when known, the SSH lifecycle `connectionStatus`. If you put a machine name on the wrong selector, Quirky reports the matching machine and the flag to use instead of returning an empty result.

`--host` also takes the bare name shown in the `name` column, on either axis — `--host trader-local` reaches the same machine as `--host ssh:ssh-1783599077486-fyasux`. Names resolve only when they are unique: a name held by two SSH targets, by two paired servers, or by one of each is refused, and the error hands back the id form for each candidate — `--host ssh:<target-id>` for an SSH target and `--host runtime:<environment-id>` for a paired server. Use those to settle it, since `--environment <server-name>` cannot separate two servers sharing a name.

## Runtime commands

```bash
quirky open --json
quirky status --json
quirky serve --port 6768 --pairing-address 100.64.1.20 --json
```

`quirky serve` starts a runtime server in the foreground without opening the desktop window. Use it for [Remote Quirky Servers](/docs/remote-servers) or headless environments, and stop it with `Ctrl-C`.

## Repos

```bash
quirky repo list --json
quirky repo add --path /abs/path/to/repo --json
quirky repo show --repo id:<repoId> --json
quirky repo set-base-ref --repo id:<repoId> --ref origin/main --json
quirky repo search-refs --repo id:<repoId> --query main --limit 10 --json
```

Set the repo base ref before creating lots of worktrees so new tasks branch from the right place by default.

## Worktrees

```bash
quirky worktree list --repo id:<repoId> --json
quirky worktree ps --json
quirky worktree current --json
quirky worktree show --worktree active --json
quirky worktree create --repo id:<repoId> --name fix-login --json
quirky worktree create --name child-task --agent codex --prompt "Investigate the flaky login test" --json
quirky worktree set --worktree active --comment "reproduced failure; testing token refresh fix" --json
quirky worktree set --worktree active --workspace-status in-review --unread --json
quirky worktree rm --worktree id:<worktreeId> --force --json
```

When `worktree create` runs from inside an Quirky-managed worktree, Quirky records the new worktree as a child when it can infer the relationship. Pass `--parent-worktree active` to be explicit, or `--no-parent` when the new work is independent.

`worktree set --unread` puts the unread dot on the workspace in the sidebar, the same one Quirky shows when an agent finishes; `--read` clears it.

Agent startup flags:

```bash
quirky worktree create --name review-api --agent claude --setup run --json
quirky worktree create --name quick-check --agent codex --prompt "Summarize the diff" --setup skip --json
quirky worktree create --name hidden-setup --setup inherit --json
```

`--agent` launches the selected agent in the first terminal. `--prompt` sends initial work to that agent. `--setup run|skip|inherit` controls repo setup hooks; `inherit` follows the repo policy.

Link issues and reviews using the existing workspace metadata:

```bash
quirky worktree create --repo id:<repoId> --name review-task --pr 123 --json
quirky worktree create --repo id:<repoId> --name gitlab-task --gitlab-issue 42 --gitlab-mr 77 --json
quirky worktree set --worktree active --gitlab-issue '#42' --gitlab-mr '!77' --json
quirky worktree set --worktree active --gitlab-issue https://gitlab.example.com/group/project/-/work_items/42 --json
quirky worktree set --worktree active --pr null --gitlab-mr null --json
```

`--pr` is a GitHub pull request number. `--gitlab-issue` accepts an issue number or `#42`; `--gitlab-mr` accepts a merge request number or `!77`. Numbers must be positive safe integers. The GitLab flags also accept HTTP(S) issue or merge request URLs, including self-hosted instances and nested groups. The URL's host and project must match the workspace's stored GitLab source context or the repository's stored remote. If that identity is missing or different, the command fails before updating metadata. A URL cannot choose another project, change the checkout, or fetch a review branch.

Omitting a flag leaves its link unchanged. On `set`, literal `null` clears only the named link; `create` refuses `null`. Each provider has separate fields, so setting a GitLab issue or merge request preserves GitHub and Linear links.

Folder-based repositories can store numeric links through these commands, but a number does not supply a provider host or project. Without existing source context or a stored remote, pasted GitLab URLs are refused and provider details or clickable links may be unavailable. These flags use fields already supported by the runtime; an older runtime that predates a field may ignore it, so check `worktree show --json` after writing to an older host.

## References

A workspace can link multiple reviews and issues, including sources outside its repository.

```bash
quirky reference list --worktree name:api --json
quirky reference add https://github.com/acme/api/pull/5123 https://linear.app/acme/issue/STA-1234 --worktree name:api --json
quirky reference remove https://github.com/acme/api/pull/5123 --worktree name:api --json
quirky reference remove --key '<key-from-list>' --worktree name:api --json
quirky worktree create --name fix --reference https://github.com/acme/api/pull/5123 --reference https://linear.app/acme/issue/STA-1234 --json
quirky reference find STA-1234 --json
```

- **Writes:** full URLs only; no custom shorthand. `remove --key` supports older entries without URLs. Source-unknown legacy links cannot match an exact URL; native issue keys remain searchable when stored. Duplicate adds and absent removals are no-ops. Unrelated links and current selection are preserved. Older hosts without safe delta merging refuse writes.
- **Create:** repeat `--reference`; incompatible with `--pr`, `--issue`, `--linear-issue`, `--gitlab-issue`, and `--gitlab-mr`. References persist before setup or agent startup.
- **Find:** a full URL or native issue key; bare numbers are rejected. Keys search all matching sources. Reads stored metadata, without provider requests or conversation searches. Use `quirky search` for conversation text.
- **Scope:** `--worktree` selects a worktree or folder workspace. Find also accepts `--repo` instead, plus `--include-archived` and `--limit` (default 50 workspaces). `truncated: true` means more matched. Remote selectors refer to the execution host; `current` is local only.
- **Output:** list returns `references` with opaque `key` and `selected`; writes also return `changes`. Worktree show/list/ps retain `linkedItems`. Find returns workspace matches and agents with `linked`, `liveness`, and available `terminal`/`mailbox` addresses. `linked: false` means ownership is unknown; sharing a workspace is insufficient evidence.

Choose an agent from `find`, then use its exact address:

```bash
quirky terminal send --terminal '<terminal-from-find>' --text 'Status?' --enter
quirky orchestration send --to '<mailbox-from-find>' --subject 'Status?' --type question
```

Mailboxes are `dispatch:<id>` or `quirky_session_id:<id>`; a `run:<id>` addresses a coordinator. Find never sends messages or assigns ownership. Adding references from a shell does not associate that shell with an agent.

## Terminals

```bash
quirky terminal list --worktree active --json
quirky terminal show --terminal <handle> --json
quirky terminal read --terminal <handle> --json
quirky terminal read --terminal <handle> --screen --json
quirky terminal read --terminal <handle> --cursor <cursor> --limit 1000 --json
quirky terminal send --terminal <handle> --text "continue" --enter --json
quirky terminal wait --terminal <handle> --for tui-idle --timeout-ms 300000 --json
quirky terminal create --worktree active --title "tests" --command "npm test" --json
quirky terminal split --terminal <handle> --direction horizontal --command "npm run dev" --json
quirky terminal rename --terminal <handle> --title "runner" --json
quirky terminal set-pane-title --terminal <handle> --title "reviewer" --json
quirky terminal switch --terminal <handle> --json
quirky terminal close --terminal <handle> --json
quirky terminal close --worktree active --all --json
```

Omit `--terminal` to target the active terminal in the current worktree. Read before sending when you are not sure what the terminal is waiting for.

Close stops the process as part of removing the terminal. Use `--terminal <handle>` for one
terminal, or `--worktree <selector> --all` to durably close every terminal in exactly that
workspace, including its saved layouts and agent-resume records. Use workspace Sleep when those
terminals should resume later. If the execution host cannot confirm that every PTY stopped, bulk
close returns a failing `unverifiable` result rather than claiming the processes exited.
`terminal stop` remains only for compatibility with older tooling.

<Callout title="Terminal handles">
  Terminal handles are runtime-scoped. If Quirky restarts or a command reports a stale terminal
  handle, run `quirky terminal list --json` and reacquire the handle.
</Callout>

`terminal list` reports each terminal's `executionHostId` when Quirky can verify it, plus a result-level `hostScope` with covered and omitted host IDs. Treat a missing host identity or scope as **unverifiable**, not local. A missing terminal is evidence that it exited only when its execution host is listed in `hostScope.hostIds`.

By default, `terminal read` returns the accumulated output stream with terminal escapes stripped. Programs that redraw lines can therefore appear as stacked fragments. Use `--screen` when you need the currently rendered frame; the response's `source` identifies `stream`, `screen`, or `screen-unavailable`. Screen reads have no history to page, so `--screen` and `--cursor` are mutually exclusive.

For long output, use cursor reads. Save `nextCursor` from one stream read, then pass it back with `--cursor` to fetch only new output.

## Files

```bash
quirky file open src/App.tsx --worktree active --json
quirky file open src/App.tsx --line 42 --column 7 --worktree active --focus --json
quirky file diff src/App.tsx --staged --worktree active --json
quirky file open-changed --mode both --worktree active --json
```

Paths are relative to the selected worktree. `--line` and `--column` are 1-based; a column requires a line. Positions are applied when you select the file, or immediately with `--focus`. Markdown switches to source view for positioning. Older hosts open the file without positioning. `open-changed` reads git status and opens changed files in edit, diff, or both modes. Tabs open without changing what you are looking at; pass `--focus` to be brought to them.

## Built-in browser

Browser commands control Quirky's embedded browser tab for the selected worktree. They do not control Chrome, Safari, or the Quirky desktop UI.

Use a snapshot -> act -> snapshot loop:

```bash
quirky goto --url http://localhost:3000 --worktree active --json
quirky snapshot --worktree active --json
quirky click --element @e3 --worktree active --json
quirky fill --element @e1 --value "user@example.com" --worktree active --json
quirky wait --text "Welcome" --worktree active --json
quirky screenshot --worktree active --json
```

Refs such as `@e3` come from `snapshot`. Re-snapshot after navigation, tab switches, clicks that change the page, and any stale-ref error.

Tab and capture commands:

```bash
quirky tab list --worktree active --json
quirky tab create --url http://localhost:3000 --worktree active --json
quirky tab switch --index 1 --worktree active --json
quirky capture start --worktree active --json
quirky console --limit 50 --worktree active --json
quirky network --limit 50 --worktree active --json
quirky full-screenshot --worktree active --json
quirky pdf --worktree active --json
```

Use `quirky exec --command "<agent-browser command>" --json` only for browser actions that do not have a typed Quirky command yet.

Browser device emulation:

```bash
quirky set device --name "iPhone 12" --worktree active --json
quirky screenshot --worktree active --json
```

## Desktop computer use

Use `quirky computer` for native desktop apps outside the built-in browser:

```bash
quirky computer permissions --json

```

## Mobile emulator

The mobile emulator commands control iOS Simulator devices through Quirky's worktree-scoped bridge. Use them instead of raw `serve-sim` or `simctl` when an agent is operating from inside Quirky, so lifecycle and active-device state stay attached to the current worktree.

```bash
quirky emulator list --worktree active --json
quirky emulator attach "<device-name-or-udid>" --worktree active --json
quirky emulator tap 0.5 0.7 --worktree active --json
quirky emulator type "hello" --worktree active --json
quirky emulator gesture '[{"type":"begin","x":0.5,"y":0.8},{"type":"move","x":0.5,"y":0.4},{"type":"end","x":0.5,"y":0.2}]' --worktree active --json
quirky emulator button home --worktree active --json
quirky emulator rotate landscape_left --worktree active --json
quirky emulator exec --command "tap 0.5 0.7" --worktree active --json
quirky emulator kill --worktree active --json
quirky emulator shutdown --worktree active --json
```

Coordinates are normalized from `0` to `1`. Prefer `tap` for single taps, and use `gesture` for drags or multi-step touch input. Pass `--device <udid-or-name>` or `--emulator <id>` when a script must target a specific simulator instead of the worktree's active emulator.

## Linear

The `quirky linear` surface is what agents use via the `quirky-linear` skill (legacy install name `linear-tickets` still works). Prefer `--json`. Linked worktrees resolve with `--current`.

### Read

```bash
quirky linear issue --current --full --json
quirky linear issue ENG-123 --comments --children --relations --activity --json
quirky linear search "auth bug" --workspace all --json
quirky linear list --filter assigned --limit 10 --json
quirky linear list-issues --team ENG --state started --assignee me --json
quirky linear list-issues --query auth --updated-at -P7D --cursor <cursor> --workspace <id> --json
quirky linear team list --json
quirky linear team states --team ENG --json
quirky linear team labels --team ENG --json
quirky linear project list --query launch --json
```

`--full` expands comments, children, attachments, relations, and activity. Section flags (`--comments`, `--children`, `--attachments`, `--relations`, `--activity`) work individually.

### MCP-style write

```bash
# Create or update (omit id/--current to create; requires --team and --title on create)
quirky linear save-issue --team ENG --title "Fix auth" --priority high --json
quirky linear save-issue ENG-123 --state "In Progress" --assignee me --json
quirky linear save-issue --current --project null --due-date null --json

quirky linear relation add ENG-1 --related ENG-2 --type blocks --json
quirky linear relation remove ENG-1 --related ENG-2 --type related --json
```

`save-issue` labels **replace** the full label set (Linear MCP `save_issue` semantics). Literal `null` clears assignee, estimate, due date, project, or parent.

### Field helpers (still valid)

```bash
quirky linear status set --current --to "In Progress" --json
quirky linear assignee set --current --me --json
quirky linear priority set ENG-123 --to high --json
quirky linear estimate set --current --to 3 --json
quirky linear due-date set --current --to 2026-08-01 --json
quirky linear label add --current --label backend --json
quirky linear comment add --current --body "Investigating regression" --json
quirky linear attach --current --url https://example.com/repro --title "Repro" --json
quirky linear create --title "Flaky login test" --team ENG --priority high --json
```

Run `quirky linear --help` or `quirky skills get quirky-linear` for the version-matched list. Pass an explicit issue id (e.g. `ENG-123`) when a script may run outside an Quirky-linked worktree.

## Skills (local, no runtime required)

List bundled guides, print a version-matched guide, or install/update hybrid skill packages without the desktop Settings UI:

```bash
quirky skills list
quirky skills get quirky-cli
quirky skills get orchestration --references
quirky skills get orchestration --reference recovery-and-cleanup
quirky skills get orchestration --full
quirky skills install --skill quirky-cli --skill orchestration
quirky skills install --all --dry-run
quirky skills update --all
```

`install` / `update` shell out to the same `npx skills` commands Settings uses. They do not contact the Quirky runtime. See [Quirky skills](/docs/cli/skills#keep-skills-up-to-date).

## Account (host-local runtime)

On a headless host running Quirky (`quirky serve` or the desktop app), add managed Claude/Codex accounts when the remote client cannot use **Add account** (remote runtime scope disables that button):

```bash
quirky account list
quirky account add                 # Claude by default
quirky account add --agent codex
```

`account add` runs `claude login` / `codex login` in **this** terminal on the host, then registers the captured credentials with the local runtime. Codex uses device authorization so the browser can finish on another machine. Run these on the machine that owns the accounts — not through a client-only remote session.

## Automations, environments, and hooks

Scheduled prompts:

```bash
quirky automations list --json
quirky automations create --name "Daily review" --trigger daily --time 09:00 --prompt "Review open changes" --provider codex --repo id:<repoId> --disabled --json
quirky automations run <automationId> --json
```

Remote runtime environments:

```bash
quirky environment add --name work-laptop --pairing-code "quirky://pair?code=..." --json
quirky environment list --json
quirky environment rm --environment <selector> --json
```

Agent status hooks:

```bash
quirky agent hooks status --json
quirky agent hooks on --json
quirky agent hooks off --json
```

## Agent habits

- Prefer `--json` for automation and agent calls.
- Prefer selectors over parsing UI labels.
- Read terminal state before sending input unless the next input is obvious.
- Use worktree comments for progress checkpoints. See [Worktree checkpoints](/docs/cli/worktree-checkpoints).
- Use [Orchestration](/docs/cli/orchestration) for tracked multi-agent dispatches instead of ad hoc terminal prompts.
